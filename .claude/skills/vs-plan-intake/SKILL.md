# 기획서 반영 절차

## 원칙
- 기획서 원본은 노션 `VishaSTD / VishaSynapse`와 하위 페이지(`[Synapse-…]` 페이지). 상위 페이지와 다른 프로그램 페이지는 보지 않는다. 이 프로젝트는 `[Synapse]` 항목만 본다. **사람이 작성·점검하고 Claude는 읽기만 한다.** (노션 쓰기 도구는 deny)
- 기획서대로 무조건 만들지 않는다. 구현 전에 확인하고, **답을 받기 전에는 추측으로 채우지 않는다.**
- 기획서 수정이 필요해 보이면 직접 고치지 않고 "기획 검토 요청"으로 알린다.

## 1. 읽기
- 노션 검색·조회 도구로 해당 페이지를 읽는다. 페이지의 마지막 수정 시각을 기록해 둔다.
- 비교 대상: 현재 코드, `docs/ARCHITECTURE.md`, `docs/tech_spec/`, worklist.

## 2. 검토 (항목마다)
| 관점 | 예 |
|---|---|
| 실현 가능성 | API·라이브러리 제약 (공식 API에 없는 데이터 등) |
| 누락 | 데이터 형식, 예외·실패 시 동작, 빈도·크기 |
| 충돌 | 다른 기획 항목, 기존 결정, 현재 코드와 다름 |
| 위험 | 보안, 안정성, 성능 |

## 3. 보고 (사용자에게)
- 일치 / 불일치(노션↔코드, 노션↔명세) / 결정 필요 질문으로 나눠 보고한다.
- 각 항목에 근거를 단다: 노션 페이지와 기획 태그(`[Synapse-<영역>-<이름>]`, 예: `[Synapse-DB-Connect]`. 기획 항목에 붙이며 작업 단위가 아니다. 이름은 중복·변경·재사용하지 않는다), 코드는 파일:줄.
- 태그 형식이 어긋나거나 중복이면 함께 알린다. (한 태그는 한 항목, 번호 재사용 금지)

## 4. 기술 명세로 옮기기 (합의 후)
- `docs/tech_spec/NN_<주제>.md`에 작성한다. 상단에 상태(`초안`/`승인`)와 근거 노션 페이지·수정 시각을 적는다.
- 모든 항목에 근거 태그를 달고 다음 셋으로 구분한다.
  - `확정`: 기획서에 명확히 적힌 것
  - `해석`: 모호한 부분을 보충한 것 (근거와 다른 선택지 포함, 사용자 승인 필요)
  - `확인 필요`: 결정이 필요한 것
- 기획서에 없는 요구사항은 `AI 제안`으로 분리한다.

## 5. 작업으로 나누기
- worklist 항목 형식: `- [ ] <번호> <내용> — 기획: [태그] / 명세: <문서> §<절>`
- GitHub 이슈로 관리하는 경우 `vs-issue` 스킬의 `task.md` 형식으로 초안을 만들고 승인받는다.
