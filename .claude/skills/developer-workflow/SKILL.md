# 코드 수정 절차

## 0. 기준
- 구현 기준은 기술 명세(`docs/tech_spec/`) 하나다. 노션 원본은 보지 않는다(메인 세션이 명세로 정리한다).
- 프로토콜(시그니처, 메시지 형식, 에러 코드)은 명세 02에서 읽는다. 스킬·기억에 의존하지 않는다.
- 명세에 없는 것을 정해야 하면 developer 에이전트 정의의 "명세에 없는 것을 만났을 때"를 따른다: 사용자 판단이 꼭 필요한 것만 멈추고 질문, 나머지는 보수적인 동작으로 구현하고 "이슈 후보"로 적은 뒤 계속한다.
- 이 스킬의 규칙과 어긋나는 작업이 필요하면(예: 기존 파일을 통째로 다시 쓰기) **하기 전에** 멈추고 "규칙 예외 제안"으로 이유와 함께 돌려준다.

## 1. 분석
- `docs/work/worklist.md`에서 맡은 항목의 내용과 근거(기획 태그, 명세 절)를 확인하고, 그 명세 절을 읽는다.
- 대상 파일을 처음부터 끝까지 읽고, Grep으로 사용처(`require`, 호출부)를 찾아 영향 범위를 확인한다.
- 넘겨받은 수정 방향과 실제 코드가 맞지 않으면(이미 고쳐짐, 방향대로 하면 다른 곳이 깨짐) 수정하지 말고 보고한다.

## 2. 수정
- 넘겨받은 항목과 승인된 방향만 구현한다. 명세에 적힌 파일·함수·설정·메시지만 새로 만든다. 더 필요해 보이면 만들지 말고 제안으로 보고한다.
- `node-coding-rule` 스킬의 표준을 따른다. Edit로 수정하고, 줄바꿈(CRLF)과 인코딩을 유지한다.
- 쓰기 대상은 소스 코드(`*.js`)와 `.temp/`뿐이다. `package.json`·문서·`.claude/`·worklist는 메인 세션이 명시한 경우만.
- 범위 밖에서 발견한 것(다른 문서·규칙 수정 필요, 명세 밖 버그)은 고치지 않고 보고에만 적는다. 이슈와 커밋은 만들지 않는다(메인 세션이 한다).
- 단위 테스트(`test/`)는 쓰지 않는다(qa가 명세 기준으로 쓴다).

## 3. 자체 확인 (에러가 없는지만 본다)
1. **문법 검사** (프로젝트 전체):
   ```bash
   find . -name '*.js' -not -path './node_modules/*' -not -path './.claude/*' -print0 | xargs -0 -n1 node --check
   ```
2. **모듈 로드** (바뀐 모듈마다): `node -e "require('./<파일>')"`. require하는 순간 외부 통신이 일어나는 모듈이면 실행하지 않고 보고에 적는다.
3. **로컬 기동** (중계 서버 관련 변경일 때). 사용자가 기본 포트로 서버를 띄워 둘 수 있으므로 기본이 아닌 포트(예: 47125)를 쓴다:
   ```bash
   node -e "require('./VishaSynapse/VSServer').SocketServer(47125); setTimeout(() => process.exit(0), 1500)"
   ```
   - 에러 없이 기동 로그가 나오고 1.5초 뒤 종료되면 통과. 포트가 이미 사용 중(`EADDRINUSE`)이면 실패로 보지 말고 그 사실만 보고한다.
4. **동작 테스트** (가짜 클라이언트로 메시지·타이머를 확인할 때):
   - 스크립트는 `.temp/`(git 제외)에 **Write 도구로** 만든다. 셸 heredoc이나 Claude 임시 폴더(scratchpad)는 쓰지 않는다.
   - 실행은 `node .temp/<파일>.js` **한 줄로만** 한다(다른 명령을 붙이면 허용 규칙에 맞지 않아 승인 요청이 뜬다).
   - `127.0.0.1`과 기본이 아닌 포트만 쓴다. DB, 치지직, `VishaCore.js`, `.env`는 다루지 않는다. `.temp/` 스크립트는 승인 없이 실행되므로 이 제한을 반드시 지킨다.
   - 대상: 실사용에서 일어나기 어려운 실패 경로(에러 코드, 시간 초과, 용량 초과)와 정상 연결 1개. 실제 기기 연동과 장시간 안정성은 사용자가 테스트한다.
   - 끝나면 스크립트를 지운다.

## 4. 보고 형식 (유일한 기준)
1. **처리 항목**: 항목 번호, 기획 태그, 구현한 명세 절. 항목마다 완료 / 질문으로 멈춤 / 규칙 예외 제안. 구현하며 세운 가정.
2. **흐름 대응표**: `함수(파일:줄) → 명세 § → 확인 방법과 결과` 표. 명세의 동작이 곧 확인 기준이다(따로 계획을 세우지 않는다). 사용자는 C#에 익숙하므로 낯선 JS 개념은 C# 대응을 짧게 붙인다.
3. **변경 파일**: 파일:줄, 한 줄 요지.
4. **자체 확인**: 문법 검사·로드·기동·동작 테스트 각각 통과/실패, 실행하지 못한 것과 이유. 동작 테스트를 했으면 "확인한 항목"과 "사용자가 확인할 항목"을 나눈다.
5. **범위 밖 발견**: 손대지 않은 문제와 어디를 고쳐야 하는지.
6. **사용자 질문**(멈춘 항목)과 **이슈 후보**(상황, 구현해 둔 임시 동작, 다른 선택지)를 나눠 적는다.
7. **문서 반영 내용**: 명세 "구현 현황"에 넣을 줄, 모듈 구조가 바뀌었으면 `docs/ARCHITECTURE.md`에 넣을 내용(모듈, 역할, 의존 관계).

## 5. 병행 작업 (developer 백그라운드 + 메인 세션 논의·테스트)
1. **명세 고정:** developer가 작업 중인 항목의 명세 절은 끝날 때까지 고치지 않는다. 그 사이 논의로 바뀐 내용은 다음 항목으로 넘긴다.
2. **쓰기 영역 분리:** developer는 `*.js`·`.temp/`, 메인 세션은 `docs/`·`.claude/`·`CLAUDE.md`·worklist.
3. **테스트 분리:** 사용자 테스트는 완료·커밋된 항목으로 한다. 사용자가 서버를 띄워 둔 동안에는 developer에게 기본이 아닌 포트를 쓰라고(또는 로컬 기동을 하지 말라고) 전달한다.
4. developer가 질문·"규칙 예외 제안"으로 돌아오면 사용자와 정리한 뒤 SendMessage로 같은 developer에게 이어서 맡긴다. 이슈 후보는 메인 세션이 바로 이슈로 올린다(`vs-git`).
