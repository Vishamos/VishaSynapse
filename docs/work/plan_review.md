# 기획 검토: 남은 질문

노션 기획서에 반영이 필요한 질문 목록. **노션에서 가닥이 잡힌 내용은 기술 명세(`docs/tech_spec/02_relay_server.md`)로 옮기고 여기서 지운다.** A 그룹이 비면 명세 02를 `승인` 단계로 올린다.

## 진행 방식
1. 사용자가 노션에 답을 반영한다. 자문이 필요한 부분은 줄 앞에 `//`를 붙인다 (명세로 옮기지 않고 의견을 단다).
2. Claude가 노션을 다시 읽고 각 항목의 **완료 기준**을 충족하는지 본다.
3. 충족한 내용은 명세로 옮기고 항목을 지운다. 부족하면 무엇이 빠졌는지 항목에 덧붙인다.

## 범위와 기준
- 이 프로젝트는 **서버가 알아야 동작하는 것**만 본다 (명세 02 §1). 다른 프로그램 페이지는 서버와 주고받는 부분만 읽는다.
- 노션이 기획 원본이다.
- 마지막 확인: 2026-11-16, `붸쉐뭬 노션 / VishaSynapse` 수정 시각 11:27

질문 순서는 노션 `VishaSynapse` 페이지 순서(핵심 루프 → 메시지 형식 → 직접 관리 요소 → 프로그램 리스트)를 따른다.

## A. 명세 02 승인 전에 필요

### 핵심 루프

#### Q2. "프로그램 연결 체크"와 "종료 호출"
- 근거: 핵심 루프 "프로그램 연결 체크", "종료 호출 시 종료"
- 질문 1: 연결 체크는 무엇인가? (a) 접속 후 등록(Init)을 확인하는 것, (b) 접속 중인 프로그램이 살아 있는지 주기적으로 확인하는 것, (c) 둘 다
- 질문 2: 종료는 누가 호출하는가? 콘솔(Ctrl+C), VishasController의 명령, 또는 둘 다? 종료할 때 접속한 프로그램들에게 알리는가?
- 추천: 연결 체크는 (c) — 등록 시간 제한 + 주기적 확인(WebSocket ping)으로 끊긴 연결 정리. 같은 ping으로 프로그램별 왕복 지연(ms)을 재서 상태값으로 둔다(DB는 명세 02 §7.2.9c에서 같은 방식으로 확정). 종료는 우선 콘솔만, Controller 종료 명령은 나중. 종료 시 접속한 프로그램에 알림.
- 완료 기준: 노션 핵심 루프에 두 문장의 의미.

### 메시지 형식

#### Q3. 텍스트 메시지의 형식
- 근거: `VishaSynapse` "메세지 형식 — 간단한 명령: 일반 message, 실시간 데이터: Binary" (명세 02 §6.1 확정)
- 참고: `VishasController`의 기능(화면 전환, 마이크 음소거, 녹음 시작, 방송 여부 체크, 캐릭터 배치 변경)이 "간단한 명령"에 해당할 것으로 보인다.
- 질문: 텍스트 메시지는 어떤 모양인가? 목적지·명령·값을 어떻게 적는가?
- 추천: JSON. 예: `{"to": 10, "type": "명령 이름", "data": {...}}`. 서버는 `to`만 보고 전달하고 나머지는 해석하지 않는다.
- 완료 기준: 노션에 텍스트 메시지 예시 1개 (목적지 표기 포함).

#### Q4. 바이너리 바이트 배치와 타입 번호
- 근거: `VishaSynapse` "처리 받을 메세지 타입" `00 Send Handshake`, `01 Socket Client Init.`, `21 Send Face Data`
- 해소: `00`이 연결 직후 핸드셰이크라는 점은 이름으로 확인됨.
- 남은 문제
  - 타입 `21`(Send Face Data)이 기기 식별값 `21`(Galaxy)과 같은 숫자다. 우연인지, 타입 번호를 보낸 기기 식별값에 맞춘 규칙인지 불명확.
  - 목적지가 0이 아닌 메시지에도 타입 바이트가 있는지 정의가 없다.
  - `VishasController` "방송 여부 체크"처럼 **응답이 필요한 요청**은 응답을 요청한 프로그램에게 돌려보내야 한다. 그러려면 메시지에 보낸 기기가 드러나야 한다.
- 질문: 바이트 배치는? 받는 쪽이 보낸 기기를 알아야 하는가?
- 추천: 클라이언트는 `[목적지, 타입, 페이로드...]`로 보내고, 서버가 전달할 때 `[목적지, 보낸 기기, 타입, 페이로드...]`로 보낸 기기를 붙인다. 응답 경로와 Q7의 동시 송신 문제가 함께 풀린다.
- 완료 기준: 노션에 바이트 배치 1개, 타입 번호 표(번호 → 이름 → 방향), 타입 번호 규칙.

### 접속·에러 (노션에 아직 자리 없음)

#### Q5. LAN 기기의 등록 인증
- 근거: 송출컴의 서버에 휴대폰·게임컴이 같은 공유기 안에서 접속한다 (명세 02 §3.2). 지금은 LAN 안의 아무 기기나 등록할 수 있다.
- 질문: 등록할 때 공유 키를 확인하는가?
- 추천: 공유 키 확인. 값은 `.env`의 `ENV_RELAY_KEY`(가칭)에 둔다.
- 완료 기준: 노션에 인증 여부.

#### Q6. 에러 메시지
- 근거: 옛 노션 `프로토콜` "VishaSynapse — 에러가 났을 때" (재배치 후 이 문장은 사라짐)
- 질문: 서버가 프로그램에게 에러를 알리는가? 알린다면 형식과 코드 목록은?
- 추천: 텍스트 메시지(Q3 형식)로 알린다. 드물게 오가는 "간단한 명령"에 가깝다. 처음 코드는 4개 — 미등록, 알 수 없는 목적지, 형식 오류, 대상 없음. 에러 후에도 연결은 유지.
- 완료 기준: 노션에 에러를 알리는지, 형식과 코드 표, 에러 후 연결 유지 여부.

#### Q7. 동시 송신과 데이터 크기·빈도
- 근거: 다중 접속 허용 (명세 02 §5.1, 사용자 답변). 실시간 데이터를 보내는 프로그램: Face(21·22), `VishasBody`(웹캠 바디 트래킹), `VishasReflex`(키·마우스 입력)
- 질문 1: **보내는 쪽**이 여럿일 때. 예: 본방용·개발용 Face가 동시에 Vishamos로 보내면 Vishamos는 두 데이터를 섞어 받는다. (a) 받는 쪽이 보낸 기기로 걸러냄 — Q4의 "보낸 기기" 필요, (b) 등록 시 본방/개발 구분값을 받아 개발용끼리만 잇기, (c) 운영상 동시에 켜지 않음
- 질문 2: 메시지 하나의 최대 크기와 초당 횟수는? (Face, Body, Reflex 각각 대략)
- 추천: 동시 송신은 (a). 크기는 모르면 서버 한도를 넉넉히(예: 64KB) 잡고 실측 후 조정.
- 완료 기준: 노션에 동시 송신 처리, 대략의 크기·빈도(또는 "실측 후 결정"). 명세 02 §5.2 해석(같은 식별값 모두에게 전달) 승인.

### 직접 관리 요소

#### Q8. 치지직 연결 실패와 목적지 31 (`[Synapse-Chzzk]`)
- 근거: `[Synapse-Chzzk]Chzzk API` "채팅 내역 및 방송 관리". 방송 관리는 나중으로 미룸 (명세 02 §7.1.5). 페이지 내용은 아직 한 줄.
- 질문 1: 치지직 연결이 실패하거나 끊기면? `[Synapse-DB-Connect]`처럼 재시도·상태값을 둘 것인가?
- 질문 2: 지금 프로그램이 목적지 31로 메시지를 보내면 서버는 어떻게 하는가?
- 추천: DB와 같은 틀(재시도 설정, 연결 상태 enum)로 맞춘다. 31로 온 메시지는 서버가 처리할 목적지로 예약하고, 아직 기능이 없으면 에러로 응답한다(Q6).
- 참고: `[Synapse-DB]` 페이지 구성(사용 기술 / 목표 / 핵심 루프 / 세부 항목 태그)이 명세로 옮기기 좋은 형태다. `[Synapse-Chzzk]`도 같은 틀로 쓰면 된다.
- 완료 기준: `[Synapse-Chzzk]`에 실패 시 동작과 31 처리 방식.

#### Q14. DB 작업 프로토콜 (`[Synapse-DB-Protocol]`)
- **요약: 노션 요청 요소(Database·Table·ID)를 프로그램이 정하면 보안 위험. 작업 이름 방식 추천.** (노션 12:58 기준 그대로)
- 해소 (명세 02 §7.2.11): 프로그램이 Synapse를 통해 DB 작업을 JSON으로 요청하고, 결과(0 성공 / 1 이상 실패, 실패 사유)를 "보내야 할 곳"으로 받는다.
- 위험: 요청에 **쿼리나 DB·테이블 이름을 그대로 받으면**, 같은 LAN의 아무 프로그램이나 DB의 모든 데이터를 읽고 지울 수 있다. 비밀 값 테이블(`secret_store`)도 포함된다. 노션의 "그냥 쿼리가 맞을까"는 이 이유로 피하는 것이 좋다.
- 추천: **미리 정한 작업 이름**만 받는다. 예: `{"op": "viewer.get", "uid": "...", "replyTo": 10}`, `viewer.add`, `viewer.update`, `viewer.remove`. 서버가 작업 이름별로 정해진 질의를 실행하고, DB·테이블은 서버가 안다(요청에 넣지 않음). `secret_store`는 이 프로토콜로 접근할 수 없게 한다.
- 질문
  1. 위 방식(작업 이름 목록)으로 할까? 그렇다면 처음 필요한 작업 목록은?
  2. 어떤 프로그램이 DB 작업을 요청하는가? (Vishamos? Controller?) 쓰기(추가·수정·제거)까지 허용할 프로그램은?
  3. 실패 코드 목록은 Q6(에러 메시지)과 하나로 합칠까?
  4. "보내야 할 곳" 기본값이 보낸 프로그램이면, 서버가 보낸 프로그램을 알아야 한다(Q4의 "보낸 기기").
- 완료 기준: 요청 형식(작업 이름 방식 여부), 작업 목록, 요청 가능한 프로그램.

## B. 나중에 정해도 됨

### 프로그램 리스트

#### Q9. 새 프로그램의 식별값
- 근거: `붸쉐뭬 노션` 프로그램 목록 — `VishasController`, `VishasReflex`, `VishasBody`, 워치 심박수(준비중). `VishaSynapse` 시그니처 표에는 없음.
- 확인할 것: `VishasReflex`("메인컴에서 입력받은 키나 마우스값을 전송")가 다이어그램의 `VishasGameCom`(게임컴, 키 입력)과 같은 프로그램인가? 메인컴은 송출컴과 게임컴 중 어느 쪽인가?
- 질문: 각 프로그램의 식별값, 또는 번호 규칙 (예: 10단위 = 종류, 1단위 = 변형)
- 완료 기준: `VishaSynapse` 시그니처 표에 번호 추가.

#### Q10. OBS는 누가 연결하는가
- **불일치: `VishaSynapse` 다이어그램·`VishasController`(서버가 OBS 제어) ↔ 노션 배치(OBS가 직접 관리 요소에서 빠짐)**
- 근거 (서로 다름)
  - 서버가 연결: `VishaSynapse` 다이어그램 `vs --> obs : OBS Interface 조종`, 시그니처 `51 : OBS`, `VishasController` "서버에 메세지를 보내 유니티와 OBS를 컨트롤"
  - 서버 밖: 재배치 후 `OBS_WebSocket`이 `VishaSynapse`의 "직접 관리 요소"가 아니라 별도 프로그램으로 분리됨
- 질문: obs-websocket에 접속하는 것은 VishaSynapse인가, VishasController인가?
- 추천: VishaSynapse. Controller의 프리셋(OBS + Vishamos 일괄 제어)이 서버 한곳에서 처리되고, obs-websocket 비밀번호도 한곳(`secret_store`)에만 둔다. 이 경우 "직접 관리 요소"에 `[Synapse-OBS]` 페이지를 추가하고, 서버가 처리할 OBS 명령(화면 전환, 마이크 음소거, 녹음 시작, 방송 여부 체크)을 적는다.
- 완료 기준: 노션에 연결 주체. 서버라면 직접 관리 요소에 OBS 페이지와 명령 목록.

### 직접 관리 요소

#### Q11. 시청자 데이터의 필드와 보관
- 해소: 시청자 데이터를 저장한다 — 치지직 계정 UID와 UID별 일부 데이터, 개인정보 제외 (명세 02 §7.2.2). 추가·제거·수정을 한다 (`[Synapse-DB]` 핵심 루프).
- 남은 질문
  1. "일부 데이터"는 무엇인가? (예: 닉네임, 첫 채팅 시각, 누적 채팅 수, soft currency 잔액)
  2. 언제 추가·수정·제거하는가? (예: 첫 채팅 시 추가, 채팅마다 수정, 시청자 요청 시 제거)
- 위험 (확인 필요, 추측 아님)
  - **UID가 개인정보가 아닌지는 단정할 수 없다.** UID만으로는 누구인지 모르더라도, 닉네임이나 채널 정보와 결합하면 특정 개인을 알아볼 수 있어 개인정보로 볼 여지가 있다. 저장 전에 치지직 Open API 이용 약관의 데이터 보관 조건을 확인해야 한다.
  - 닉네임을 함께 저장하면 개인정보 쪽으로 더 가까워진다. 꼭 필요한 필드만 둘 것.
  - 옛 계획의 "팔로우 기간"은 공식 API 이벤트에 들어오는지 아직 확인하지 않았다.
- 완료 기준: `[Synapse-DB]`에 필드 목록과 추가·수정·제거 시점, 보관 기간. (약관 확인은 구현 전 Claude가 문서로 확인해 보고)

- **태그 형식:** `[Synapse-DB-Connect]`, `[Synapse-DB-Status]`처럼 번호 대신 이름을 쓰셨다. 번호보다 읽기 쉽고 중간 삽입 문제도 없다. 지킬 것: 같은 이름을 두 번 쓰지 않기, 한 번 붙인 이름은 바꾸지 않기(바꾸면 명세·커밋의 근거가 끊김), 폐기한 이름은 재사용하지 않기.
- **README:** 재배치 후 "REST API같은" 표현이 노션에서 사라졌다. README의 "REST API"는 표현 수정으로 처리한다 (worklist E2).
- 용어 통일: VishaSynapse / Synapse, Visha / Vishas, Galaxy / Android, Iphone / iOS가 섞여 있다.
