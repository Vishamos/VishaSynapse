# 기획 검토

절차는 `visha-common:design-work` 2절. 노션은 사용자가 쓰고 Claude는 읽기만 한다.

## 범위와 기준
- 노션 `VishaSTD / VishaSynapse` 페이지와 하위 `[Synapse-…]` 페이지만 본다. 그 안에서도 **서버가 알아야 동작하는 것**만 다룬다 (명세 02 §1).
- 마지막 확인: 2026-11-18, `VishaSynapse` 11-17 17:00 (A2 Q20∼Q24 반영), `[Synapse-DB]`·`[Synapse-OBS]`·`[Synapse-Chzzk]`·`[Synapse-Discord]` 11-17 04:35 (내용 변화 없음)
- 자문 표시: 노션 줄 앞 `//`는 Claude에게 자문 요청이다(명세로 옮기지 않음). `//mermaid`는 근처의 `->` 흐름을 mermaid 코드로 옮겨 달라는 뜻이며, 해석한 곳을 코드 아래 적어 둔다.
- 그림(mermaid)은 꾸미기 용도라 그림에만 있는 내용은 근거로 삼지 않는다 (2026-11-17).
- 사용자가 노션에 옮긴 항목은 Claude가 다시 읽고 확인한 뒤 이 문서에서 바로 지운다(해결 표시·취소선을 남기지 않는다).

## 노션에 적을 것
코드 작업은 막지 않는다(명세는 합의한 값으로 반영됨).

### 치지직 → 컨트롤러 (2026-11-25 결정, 아래 "결정됨")
- `[Synapse-Chzzk]`: `[보류]` 해제, 채팅만(후원은 나중), 끊기면 무한 재시도, 상태 4개(`disabled` 포함), 101로 오는 명령 없음(501)
- `[Synapse-Message-Signature]`: 컨트롤러 41
- `[Synapse-Message-Command]`: 이벤트 `chzzk.chat`·`chzzk.status`를 41로, 41 등록 직후 현재 상태 1회
- `[Synapse-Loop]`: 치지직 사용 여부 = config `Chzzk.ClientId`, 치지직은 서버 시작을 막지 않음

### 메시지·에러
- `[Synapse-Message-Command]`에 한 줄: "직접 관리 요소가 먼저 보내는 이벤트의 `from`은 그 요소의 시그니처(예: 치지직 채팅은 101)". 지금은 태그 없는 "서버 역할" 절에만 있다
- `[Synapse-Message-Relay]` 에러 코드가 한 줄씩 밀려 있다: 받을 대상 없음(JSON) `400` → `404`, `from` 불일치(JSON)에 `400` 추가, 등록되지 않은 기기 `1008` → `401`, `from` 불일치(Binary) "연결을 끊는다 `1008`" 한 줄 추가
- 에러 표 `from-mismatch` → `from_mismatch`(코드에서 쓰는 문자열). 404 사유에 "(연결된 클라이언트 없음 포함, JSON만)" 추가
- 에러 표 사유 칸의 채팅 문구 정리: "(노션의 \"규격 외 프로토콜 메세지 수신\")", "(Q5 ①을 둘 경우)" 삭제
- `[Synapse-Message-Error]`의 `//` 자문 답: 그 방향으로 좋다. 서버 쪽 조건은 하나뿐이다 — **모든 클라이언트는 JSON을 받을 수 있어야 한다**(등록 답장·에러가 JSON). 바이너리 송수신 여부는 각 클라이언트 사양에 적는다. 확인했으면 `//` 줄을 이 문장으로 바꾼다
- 규격 표 `"To", "From", "Type(도착지가 서버면)"` → 소문자 `to`·`from`·`type`, "도착지가 서버면" → "서버가 보내거나 받을 때", `index` 설명 "배열에 등록한 인덱스" → "연결 번호"
- 규격 표 "`data` 상세 규격은 각 Relay" → "각 클라이언트·직접 관리 요소 페이지". (선택) 시그니처 절 "서버는 서버 시그니처의 데이터를 처리하고…"는 Command·Relay 절과 겹친다

### 시그니처·연결
- 시그니처 절에 한 줄씩: "x0 값(10·20·30)은 나중에 기기 묶음이 필요할 때를 위해 비워 둔다", 11 비고 "테스트 클라이언트도 11로 등록해 함께 받는다"(명세 02 §5.3)
- 연결도 mermaid: `Vishamos · 10 / 11` → `Vishamos · 11`, `Body · 30` → `Body · 31`
- `[Synapse-Message-Signature]`의 "프로토콜마다 최대 크기·초당 횟수를 용량 표에 적는다"를 2026-11-23 결정으로 고친다(아래 "결정됨")
- `[Synapse-Client-Ping]` "Pong 수신 시간(응답 유효 시간)" 아래 "응답 유효 시간." 줄 삭제(이제 ping 간격으로 판정), 클라이언트 다이어그램 `alt` 문구 "pong이 응답 유효 시간을 넘김" → "다음 ping까지 pong 없음", "재전송 횟수 만큼" → "미응답 허용 횟수만큼"

### DB

## 보류
결론이 나지 않은 것과, 정하려면 필요한 것.

#### Q19. 컨트롤러(41)로 전달할 것 (노션 `VishasController`)
- 컨트롤러 자체(기술·구조·화면)는 컨트롤러 프로젝트에서 다룬다(2026-11-25 이관). 여기서는 서버가 컨트롤러에 **전달할 것**만 정한다. 1단계(`chzzk.chat`·`chzzk.status`)는 결정됨.
- 나중 후보
  1. 서버 에러 (노션 "추후 컨트롤러에 에러메세지 전송"). 정할 것: 붙일 정보(시그니처·연결 번호, 시각), 반복 에러 묶기(명세 02 §6.12b)
  2. 클라이언트 연결 상태(접속·끊김·지연, 명세 02 §5.7). 정할 것: 바뀔 때마다 알림 / 컨트롤러 요청 시 응답
- 컨트롤러가 서버로 관리 명령을 보내게 되면 권한(등록 인증 없음, 명세 02 §5.5d)을 먼저 정한다.

#### Q14. DB 작업 프로토콜의 요청 형식 (`[Synapse-DB-Protocol]`)
- **요약: 노션 요청 요소(Database·Table·ID)를 프로그램이 정하면 보안 위험. 사용자 인지함 — Synapse를 체계적으로 정리할 때 다룬다.**
- 해소된 부분 (명세 02 §7.2.11): 프로그램이 Synapse를 통해 DB 작업을 JSON으로 요청하고, 결과(0 성공 / 1 이상 실패, 실패 사유)를 "보내야 할 곳"으로 받는다.
- 추천(그때 참고): 미리 정한 작업 이름만 받는다. 예: `{"to": 0, "type": "db.viewer.get", "data": {"uid": "...", "replyTo": 10}}`. DB·테이블은 서버가 정하고, `secret_store`는 이 프로토콜로 접근할 수 없게 한다. `[Synapse-DB]` 페이지에 "메시지 처리" 절로 둔다(명세 §6.9).
- 정하려면: 작업 목록, 요청할 수 있는 프로그램과 쓰기 허용 범위, 실패 코드를 Q6과 합칠지.

#### Q11. 시청자 데이터의 필드와 보관
- 해소된 부분: 시청자 데이터를 저장한다 — 치지직 계정 UID와 UID별 일부 데이터, 개인정보 제외 (명세 02 §7.2.2). 추가·제거·수정을 한다 (`[Synapse-DB]` 핵심 루프).
- 정하려면
  1. "일부 데이터"는 무엇인가? (예: 첫 채팅 시각, 누적 채팅 수, soft currency 잔액)
  2. 언제 추가·수정·제거하는가? (예: 첫 채팅 시 추가, 채팅마다 수정, 시청자 요청 시 제거)
  3. 보관 기간
- 위험 (확인 필요, 추측 아님)
  - **UID가 개인정보가 아닌지는 단정할 수 없다.** 닉네임이나 채널 정보와 결합하면 특정 개인을 알아볼 수 있다. 저장 전에 치지직 Open API 이용 약관의 데이터 보관 조건을 확인한다(구현 전 Claude가 문서로 확인해 보고).
  - 닉네임을 함께 저장하면 개인정보 쪽으로 더 가까워진다. 꼭 필요한 필드만 둘 것.
- 태그 제안: `[Synapse-DB-Viewer]`

#### Q13. 배포·상주 방식
- 근거: 노션에 없음. 핵심 루프 "종료 호출 시 종료"
- 사용자 자문 (2026-11-17, 노션 반영 전): PC를 켜면 자동 시작, PC를 끄면 종료, 그 외에는 항상 켜 둠.
- 정하려면: (1) Node로 직접 실행 / 단일 실행 파일, (2) 아래 고려 사항 중 무엇을 할지
- 고려 사항
  - **종료 시 토큰 저장 대기:** 치지직 Refresh Token은 1회용. 종료 신호(Ctrl+C, 콘솔 닫힘, OS 종료)를 받으면 진행 중인 저장만 짧게 기다린다. 접속한 프로그램 알림은 불필요(자동 재접속).
  - **비정상 종료 시 자동 재시작**, **이중 실행 방지**(포트 충돌), **로그 파일**(나중에 VishasController), **수동 재시작 방법**
  - 부팅 직후 DB 미준비는 DB 무한 재시도로 해결됨.
- 추천: Node 직접 실행 + Windows 작업 스케줄러(로그온 시 시작, 실패 시 재시작). 위 고려 사항 모두 포함.
- 태그 제안: `[Synapse-Deploy]`

## 태그 목록 (확정 2026-11-18)

태그는 기획 항목에 붙이는 이름이며 작업 단위가 아니다. 새 내용을 노션에 쓸 때 아래 영역 안에서 이름을 지어 붙이고 이 표에 추가한다. 형식은 `[Synapse-DB-Connect]`처럼 이름형이며, 같은 이름을 두 번 쓰지 않고, 한 번 붙인 이름은 바꾸지 않고, 폐기한 이름은 다시 쓰지 않는다.

| 영역 (작업 번호 접두어) | 사용 중 | 내용이 생기면 붙일 예정 |
|---|---|---|
| 중계 서버 (`Relay`) | `[Synapse-Loop]`, `[Synapse-Message]`, `-Message-Signature`, `-Message-Type`, `-Message-Error`, `-Message-Command`, `-Message-Relay`, `[Synapse-Client]`, `-Client-Status`, `-Client-Ping` | |
| DB (`DB`) | `[Synapse-DB]`, `-DB-Connect`, `-DB-Protocol`, `-DB-Ping`, `-DB-Status` | `-DB-Viewer` (Q11) |
| 치지직 (`Chzzk`) | `[Synapse-Chzzk]` | |
| OBS (`OBS`) | `[Synapse-OBS]` (보류) | |
| Discord (`Discord`) | `[Synapse-Discord]` (보류) | |
| 입력 (`Input`) | | `[Synapse-Input]` (#4) |
| 배포·상주 (`Deploy`) | | `[Synapse-Deploy]` (Q13, 종료 포함) |
