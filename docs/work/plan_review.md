# 기획 검토: 남은 질문

노션 기획서에 반영이 필요한 질문 목록. **노션에서 가닥이 잡힌 내용은 기술 명세(`docs/tech_spec/02_relay_server.md`)로 옮기고 여기서 지운다.** A 그룹이 비면 명세 02를 `승인` 단계로 올린다.

## 진행 방식
1. 사용자가 노션에 답을 반영한다. 자문이 필요한 부분은 줄 앞에 `//`를 붙이거나 이 문서의 질문 아래에 덧붙인다.
2. Claude가 노션을 다시 읽고 각 항목의 **완료 기준**을 충족하는지 본다.
3. 충족한 내용은 명세로 옮기고 항목을 지운다. 부족하면 무엇이 빠졌는지 항목에 덧붙인다. 내용은 반영됐는데 태그가 빠졌으면 `태그 확인` 표에 올린다.

## 범위와 기준
- 노션 `붸쉐뭬 노션 / VishaSynapse` 페이지와 그 하위 페이지만 본다. 상위·다른 프로그램 페이지는 보지 않는다.
- 그 안에서도 **서버가 알아야 동작하는 것**만 다룬다 (명세 02 §1).
- 마지막 확인: 2026-11-16, `VishaSynapse` 11:27, `[Synapse-DB]` 12:58

## 태그 확인

노션에 내용은 있지만 태그가 없는 항목. 노션을 확인할 때마다 갱신하고, 태그가 붙으면 지운다. 새 태그는 각 질문의 `태그 제안`에서 하나씩 잡는다. 바꾸고 싶으면 노션에 `//[새 태그]로 변경하는 게 좋겠다`처럼 적는다.

| 노션 위치 | 태그 제안 |
|---|---|
| `VishaSynapse` "핵심 루프" | `[Synapse-Loop]` |
| `VishaSynapse` "서버 및 클라이언트 시그니처" | `[Synapse-Signature]` |
| `VishaSynapse` "처리 받을 메세지 타입" | `[Synapse-Message-Type]` |
| `VishaSynapse` "메세지 형식" | `[Synapse-Message]` (세부는 Q3) |
| 노션에 없음: 다중 접속 허용 (사용자 답변, 명세 02 §5.1) | `[Synapse-Client-Multi]` — 노션에 적을 때 |

## A. 명세 02 승인 전에 필요

### 메시지 형식 (최우선)

#### Q3. 메시지 형식: 보낸 기기 표시, 바이너리 배치, 텍스트 형식
- **요약: 중계 서버의 핵심인 메시지 모양이 정해지지 않았다. 이미 쓰인 다른 기획(DB 결과 회신, 에러 알림, 동시 송신 구분)이 모두 이것에 기대고 있어 가장 먼저 정해야 한다.**
- 근거: `VishaSynapse` "메세지 형식 — 간단한 명령: 일반 message, 실시간 데이터: Binary"(명세 02 §6.1 확정), "처리 받을 메세지 타입" `00 Send Handshake`, `01 Socket Client Init.`, `21 Send Face Data`
- 이것에 기대는 기획
  - `[Synapse-DB-Protocol]` "결과를 보낸 사람에게 돌려보냄" → 서버가 **보낸 기기**를 알아야 한다
  - 에러 알림(Q6) → 에러를 일으킨 프로그램에게 보내야 한다
  - 동시 송신(Q7) → 받는 쪽이 출처를 구분해야 한다
- 질문
  1. **보낸 기기 표시:** 받는 쪽이 누가 보냈는지 알 수 있어야 하는가? 안다면 어디에 적는가?
  2. **바이너리 배치:** 목적지가 0이 아닌 메시지에도 타입 바이트가 있는가? 타입 `21`(Send Face Data)이 기기 식별값 `21`(Galaxy)과 같은 숫자인 것은 우연인가, "타입 번호 = 보낸 기기 식별값" 규칙인가?
  3. **텍스트 형식:** 목적지·명령·값을 어떻게 적는가?
- 추천
  - 바이너리: 프로그램은 `[목적지, 타입, 페이로드...]`로 보내고, 서버가 전달할 때 `[목적지, 보낸 기기, 타입, 페이로드...]`로 보낸 기기를 붙인다. 보내는 쪽이 출처를 속일 수 없고(서버가 등록 정보로 채움), 1·Q6·Q7이 함께 풀린다.
  - 텍스트: JSON. 예: `{"to": 10, "type": "명령 이름", "data": {...}}`. 서버가 전달할 때 `"from"`을 붙인다. 서버는 `to`만 보고 전달하고 나머지는 해석하지 않는다.
  - 타입 번호: 기기 식별값과 별개의 번호 표로 둔다(`21`은 번호를 바꾸거나 규칙을 명시).
- 태그 제안: `[Synapse-Message-Sender]`, `[Synapse-Message-Binary]`, `[Synapse-Message-Text]`, `[Synapse-Message-Type]`
- 완료 기준: 노션에 바이너리 배치 1개, 텍스트 예시 1개(목적지 표기 포함), 보낸 기기 표시 방법, 타입 번호 표(번호 → 이름 → 방향).

### 핵심 루프

#### Q2. "프로그램 연결 체크"와 "종료 호출"
- 근거: `VishaSynapse` 핵심 루프 "프로그램 연결 체크", "종료 호출 시 종료"
- 질문 1: 연결 체크는 무엇인가? (a) 접속 후 등록(Init)을 확인하는 것, (b) 접속 중인 프로그램이 살아 있는지 주기적으로 확인하는 것, (c) 둘 다
- 질문 2: 종료는 누가 호출하는가? 콘솔(Ctrl+C), 접속한 프로그램의 명령, 또는 둘 다? 종료할 때 접속한 프로그램들에게 알리는가?
- 추천: 연결 체크는 (c) — 등록 시간 제한 + 주기적 확인(WebSocket ping)으로 끊긴 연결 정리. 같은 ping으로 프로그램별 왕복 지연(ms)을 잰다(DB는 명세 02 §7.2.9c에서 같은 방식으로 확정). 종료는 우선 콘솔만. 종료 시 접속한 프로그램에 알림.
- 태그 제안: `[Synapse-Client-Ping]`(연결 체크·왕복 지연, `[Synapse-DB-Ping]`과 짝), `[Synapse-Loop-Shutdown]`
- 완료 기준: 노션 핵심 루프에 두 문장의 의미.

### 접속·에러 (노션에 아직 자리 없음)

#### Q5. LAN 기기의 등록 인증
- 근거: 송출컴의 서버에 휴대폰·게임컴이 같은 공유기 안에서 접속한다 (명세 02 §3.2). 지금은 LAN 안의 아무 기기나 등록할 수 있다.
- 질문: 등록할 때 공유 키를 확인하는가?
- 추천: 공유 키 확인. 값은 `.env`의 `ENV_RELAY_KEY`(가칭)에 둔다.
- 태그 제안: `[Synapse-Client-Auth]`
- 완료 기준: 노션에 인증 여부.

#### Q6. 에러 메시지
- 근거: 노션에 없음 (옛 페이지의 "에러가 났을 때"는 재배치 후 사라짐)
- 질문: 서버가 프로그램에게 에러를 알리는가? 알린다면 형식과 코드 목록은?
- 추천: 텍스트 메시지(Q3 형식)로 알린다. 처음 코드는 4개 — 미등록, 알 수 없는 목적지, 형식 오류, 대상 없음. 에러 후에도 연결은 유지.
- 태그 제안: `[Synapse-Error]`
- 완료 기준: 노션에 에러를 알리는지, 형식과 코드 표, 에러 후 연결 유지 여부.

#### Q7. 동시 송신과 데이터 크기·빈도
- 근거: 다중 접속 허용 (명세 02 §5.1, 사용자 답변). 실시간 데이터: Face(21·22)
- 질문 1: **보내는 쪽**이 여럿일 때. 예: 본방용·개발용 Face가 동시에 Vishamos로 보내면 Vishamos는 두 데이터를 섞어 받는다. (a) 받는 쪽이 보낸 기기로 걸러냄 — Q3의 "보낸 기기" 필요, (b) 등록 시 본방/개발 구분값을 받아 개발용끼리만 잇기, (c) 운영상 동시에 켜지 않음
- 질문 2: Face 메시지 하나의 최대 크기와 초당 횟수는?
- 추천: 동시 송신은 (a). 크기는 모르면 서버 한도를 넉넉히(예: 64KB) 잡고 실측 후 조정(`제안`).
- 태그 제안: `[Synapse-Relay-Multi]`(동시 송신), `[Synapse-Relay-Limit]`(크기·빈도)
- 완료 기준: 노션에 동시 송신 처리. 명세 02 §5.2 해석(같은 식별값 모두에게 전달) 승인.

### 직접 관리 요소

#### Q8. 치지직 연결 실패와 목적지 31 (`[Synapse-Chzzk]`)
- 근거: `[Synapse-Chzzk]Chzzk API` "채팅 내역 및 방송 관리". 방송 관리는 나중으로 미룸 (명세 02 §7.1.5). 페이지 내용은 아직 한 줄.
- 질문 1: 치지직 연결이 실패하거나 끊기면? `[Synapse-DB-Connect]`처럼 재시도·상태값을 둘 것인가?
- 질문 2: 지금 프로그램이 목적지 31로 메시지를 보내면 서버는 어떻게 하는가?
- 추천: DB와 같은 틀(재시도 설정, 연결 상태 enum, 사유 코드)로 맞춘다. 31로 온 메시지는 서버가 처리할 목적지로 예약하고, 아직 기능이 없으면 에러로 응답한다(Q6).
- 태그 제안: `[Synapse-Chzzk-Connect]`, `[Synapse-Chzzk-Status]`(DB 태그와 짝), `[Synapse-Chzzk-Command]`(목적지 31)
- 완료 기준: `[Synapse-Chzzk]`에 실패 시 동작과 31 처리 방식.

## B. 나중에 정해도 됨

#### Q14. DB 작업 프로토콜의 요청 형식 (`[Synapse-DB-Protocol]`)
- **요약: 노션 요청 요소(Database·Table·ID)를 프로그램이 정하면 보안 위험. 사용자 인지함 — Synapse를 체계적으로 정리할 때 다룬다.**
- 해소 (명세 02 §7.2.11): 프로그램이 Synapse를 통해 DB 작업을 JSON으로 요청하고, 결과(0 성공 / 1 이상 실패, 실패 사유)를 "보내야 할 곳"으로 받는다.
- 추천(그때 참고): 미리 정한 작업 이름만 받는다. 예: `{"op": "viewer.get", "uid": "...", "replyTo": 10}`. DB·테이블은 서버가 정하고, `secret_store`는 이 프로토콜로 접근할 수 없게 한다.
- 남은 질문: 작업 목록, 요청할 수 있는 프로그램과 쓰기 허용 범위, 실패 코드를 Q6과 합칠지.
- 태그 제안: 기존 `[Synapse-DB-Protocol]`

#### Q10. OBS를 서버가 직접 관리하는가
- **불일치: `VishaSynapse` 다이어그램 `vs --> obs : OBS Interface 조종`·시그니처 `51 : OBS` ↔ "직접 관리 요소"에 OBS 페이지 없음**
- 질문: obs-websocket 연결을 서버가 맡는가? 맡는다면 `[Synapse-OBS]` 페이지를 직접 관리 요소에 추가하고 서버가 처리할 OBS 명령을 적는다. 맡지 않는다면 다이어그램과 시그니처 51을 정리한다.
- 태그 제안: `[Synapse-OBS]`(맡는 경우)
- 완료 기준: 둘 중 하나로 노션이 맞춰짐.

#### Q11. 시청자 데이터의 필드와 보관
- 해소: 시청자 데이터를 저장한다 — 치지직 계정 UID와 UID별 일부 데이터, 개인정보 제외 (명세 02 §7.2.2). 추가·제거·수정을 한다 (`[Synapse-DB]` 핵심 루프).
- 남은 질문
  1. "일부 데이터"는 무엇인가? (예: 첫 채팅 시각, 누적 채팅 수, soft currency 잔액)
  2. 언제 추가·수정·제거하는가? (예: 첫 채팅 시 추가, 채팅마다 수정, 시청자 요청 시 제거)
- 위험 (확인 필요, 추측 아님)
  - **UID가 개인정보가 아닌지는 단정할 수 없다.** UID만으로는 누구인지 모르더라도, 닉네임이나 채널 정보와 결합하면 특정 개인을 알아볼 수 있어 개인정보로 볼 여지가 있다. 저장 전에 치지직 Open API 이용 약관의 데이터 보관 조건을 확인해야 한다.
  - 닉네임을 함께 저장하면 개인정보 쪽으로 더 가까워진다. 꼭 필요한 필드만 둘 것.
- 태그 제안: `[Synapse-DB-Viewer]`
- 완료 기준: `[Synapse-DB]`에 필드 목록과 추가·수정·제거 시점, 보관 기간. (약관 확인은 구현 전 Claude가 문서로 확인해 보고)

#### Q12. Discord(41)
- 근거: 시그니처 `41 : Discord`만 있고 페이지 없음
- 태그 제안: `[Synapse-Discord]`
- 완료 기준: 목적과 범위, 또는 "보류"(시그니처 표에 표시).

#### Q13. 배포·상주 방식
- 근거: 노션에 없음. 핵심 루프 "종료 호출 시 종료"
- 질문: Node로 직접 실행 / 단일 실행 파일? 방송할 때만 켜는가, 송출컴에서 항상 켜 두는가?
- 태그 제안: `[Synapse-Deploy]`
- 완료 기준: 노션에 방식 1개씩.

## 노션 정리 시 참고
- **사용자 답변 보존:** 옛 코드 블록에 달았던 답변(다중 접속 허용, 인터넷 접속 없음, 채팅 송신 제외, 31 방송 관리는 나중)은 명세 02에만 남아 있다. 원하면 노션 `VishaSynapse`에도 적어 둔다.

- **README:** "REST API" 표현은 worklist E2에서 수정한다.
