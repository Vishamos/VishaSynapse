## 진행 방식
1. 사용자가 노션에 답을 반영한다. 자문이 필요한 부분은 줄 앞에 `//`를 붙이거나 이 문서의 질문 아래에 덧붙인다.
   - `//mermaid`: 근처의 `->` 흐름을 Claude가 mermaid 코드로 옮겨 "mermaid 제안" 절을 만들어 둔다(반영되면 절을 지운다). 화살표를 해석한 곳은 코드 아래 "해석한 곳"에 따로 적는다. 사용자가 확인 후 노션에 붙여 넣는다.
2. Claude가 노션을 다시 읽고 각 항목의 **완료 기준**을 충족하는지 본다.
3. 충족한 내용은 명세로 옮기고 **이 문서에서 바로 지운다**(해결 표시·취소선을 남기지 않는다). 부족하면 무엇이 빠졌는지 항목에 덧붙인다. 내용은 반영됐는데 태그가 빠졌으면 "노션 정리"에 올린다.

## A3. 치지직 채팅 → 컨트롤러 (2026-11-25 우선순위 올림)

- **범위 (사용자 2026-11-25):** 서버는 치지직 **채팅만** 받아 **컨트롤러**로 전달한다. 후원·Vishamos 전달·컨트롤러 내부는 이 범위 밖.
- **요약:** 노션에서 Q25∼Q27이 정해지면 서버 작업(Chzzk-1∼3 + 전달)을 시작할 수 있다. 컨트롤러가 따를 통신 사양 초안은 `docs/protocol/README.md` §5a.
- **선행 조건(사용자):** 토큰은 DB `secret_store`에 저장되므로 실행 PC에서 DB 접속이 먼저 돼야 한다(worklist "사용자 조치 대기"의 실행 PC 계정·`.env`·`db-ca.pem`). 그 뒤 Client Secret 입력.

#### Q25. 치지직 보류 해제 범위 (`[Synapse-Chzzk]`)
- 불일치: 노션 `[Synapse-Chzzk]` 제목이 `[보류]`, 명세 02 §7.0.1도 보류. 명세 01·02 §7.1.2는 채팅·후원 둘 다.
- 정할 것
  1. 채팅만 받는다(사용자 결정). 노션에 "후원은 나중"으로 적는다. 앱 권한 "후원 조회"는 그대로 둬도 된다
  2. 연결 실패·끊김 시 동작(명세 02 §7.1.6). 재연결 절차는 명세 01 §5.4-8에 있다. 제안: DB처럼 무한 재시도
  3. **끊김을 컨트롤러에 알릴지.** 알리지 않으면 치지직 연결이 끊겨도 컨트롤러는 "채팅이 없는 상태"와 구분하지 못한다 — 이번 문제(채팅이 와도 모름)가 그대로 남는다. 제안: 상태가 바뀔 때 `chzzk.status`를 보낸다(README §5a 초안에 포함)
  4. 목적지 101로 오는 명령. 채팅 송신은 범위 밖(§7.1.4)이라 받을 명령이 없다. 제안: 501 유지
- 완료 기준: `[보류]` 해제, 위 1∼4

#### Q26. 채팅을 받을 곳과 형식 (`[Synapse-Chzzk]`, `[Synapse-Message-Command]`)
- 불일치: 명세 02 §7.1.3은 Vishamos(11)로 보낸다. 지금 결정은 컨트롤러.
- 제안 (README §5a 초안)
  - **JSON**, `type`은 `chzzk.chat`. 문자열 위주에 빈도가 낮아 바이너리 이점이 없다(명세 02 §6.1). 명세 01 §7의 "바이너리 프로토콜로 바꾸는 부분" 문구는 JSON으로 고친다
  - `data`에는 표시에 필요한 것만: 닉네임·역할·내용·이모지·시각. 채널 ID(`channelId`·`senderChannelId`)는 넣지 않는다(쓸 곳이 없고 Q11의 개인정보 위험)
  - 컨트롤러가 접속해 있지 않으면 버린다(쌓아 두지 않음, 에러 없음)
  - 서버 로그에는 채팅 내용·닉네임을 쓰지 않고 건수만 쓴다
- 완료 기준: 노션에 전달 대상(컨트롤러), `type` 이름, `data` 항목

#### Q14. DB 작업 프로토콜의 요청 형식 (`[Synapse-DB-Protocol]`)
- **요약: 노션 요청 요소(Database·Table·ID)를 프로그램이 정하면 보안 위험. 사용자 인지함 — Synapse를 체계적으로 정리할 때 다룬다.**
- 해소 (명세 02 §7.2.11): 프로그램이 Synapse를 통해 DB 작업을 JSON으로 요청하고, 결과(0 성공 / 1 이상 실패, 실패 사유)를 "보내야 할 곳"으로 받는다.
- 추천(그때 참고): 미리 정한 작업 이름만 받는다. 예: `{"to": 0, "type": "db.viewer.get", "data": {"uid": "...", "replyTo": 10}}`. DB·테이블은 서버가 정하고, `secret_store`는 이 프로토콜로 접근할 수 없게 한다. `[Synapse-DB]` 페이지에 "메시지 처리" 절로 둔다(명세 §6.9).
- 남은 질문: 작업 목록, 요청할 수 있는 프로그램과 쓰기 허용 범위, 실패 코드를 Q6과 합칠지.

#### Q11. 시청자 데이터의 필드와 보관
- 해소: 시청자 데이터를 저장한다 — 치지직 계정 UID와 UID별 일부 데이터, 개인정보 제외 (명세 02 §7.2.2). 추가·제거·수정을 한다 (`[Synapse-DB]` 핵심 루프).
- 남은 질문
  1. "일부 데이터"는 무엇인가? (예: 첫 채팅 시각, 누적 채팅 수, soft currency 잔액)
  2. 언제 추가·수정·제거하는가? (예: 첫 채팅 시 추가, 채팅마다 수정, 시청자 요청 시 제거)
- 위험 (확인 필요, 추측 아님)
  - **UID가 개인정보가 아닌지는 단정할 수 없다.** 닉네임이나 채널 정보와 결합하면 특정 개인을 알아볼 수 있어 개인정보로 볼 여지가 있다. 저장 전에 치지직 Open API 이용 약관의 데이터 보관 조건을 확인해야 한다.
  - 닉네임을 함께 저장하면 개인정보 쪽으로 더 가까워진다. 꼭 필요한 필드만 둘 것.
- 태그 제안: `[Synapse-DB-Viewer]`

#### Q13. 배포·상주 방식
