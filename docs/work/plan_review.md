# 기획 검토

절차는 `visha-common:design-work` 2절. 노션은 사용자가 쓰고 Claude는 읽기만 한다.

## 범위와 기준
- 노션 `VishaSTD / VishaSynapse` 페이지와 하위 `[vs-…]` 페이지만 본다. 그 안에서도 **서버가 알아야 동작하는 것**만 다룬다 (명세 02 §1).
- 마지막 확인: 2026-11-27 12:05, `VishaSynapse` 12:05, `[vs-Client-CommonConnect]` 11:54, `[vs-DB]` 11:51, `[vs-Chzzk]`·`[vs-OBS]`·`[vs-Discord]` 11:38 (제목 접두어만 변경)
- 자문 표시: 노션 줄 앞 `//`는 Claude에게 자문 요청이다(명세로 옮기지 않음). `//mermaid`는 근처의 `->` 흐름을 mermaid 코드로 옮겨 달라는 뜻이며, 해석한 곳을 코드 아래 적어 둔다.
- 그림(mermaid)은 꾸미기 용도라 그림에만 있는 내용은 근거로 삼지 않는다 (2026-11-17).
- 사용자가 노션에 옮긴 항목은 Claude가 다시 읽고 확인한 뒤 이 문서에서 바로 지운다(해결 표시·취소선을 남기지 않는다).

### 치지직 → 컨트롤러 (2026-11-25 결정, 아래 "결정됨")

### 프로토콜 세부 (2026-11-27 결정: 노션은 protocol README 링크로 대신한다)
- 노션 메시지 표의 문구 정리는 하지 않는다(사용자가 노션을 따로 갱신 중, 세부 기준은 README)
- 단 `[vs-Message-Type]`에 넣은 `config.get`·`config.set`·`log` 행은 지우거나 "중계(서버는 처리 안 함)"를 붙이는 것을 권한다. 서버가 처리하는 메시지 표 안에 있어 `to: 0`으로 보내는 것으로 읽힌다(README §5b가 기준)
- `[vs-Message-Error]`의 `//` 자문 답: 그 방향으로 좋다. 서버 쪽 조건은 하나뿐이다 — **모든 클라이언트는 JSON을 받을 수 있어야 한다**(등록 답장·에러가 JSON). 바이너리 송수신 여부는 각 클라이언트 사양에 적는다. 확인했으면 `//` 줄을 이 문장으로 바꾼다
- 시그니처 표 41 `Contoller` → `Controller`

### 시그니처·연결
- 시그니처 절에 한 줄씩: "x0 값(10·20·30)은 나중에 기기 묶음이 필요할 때를 위해 비워 둔다", 11 비고 "테스트 클라이언트도 11로 등록해 함께 받는다"(명세 02 §5.3)
- 연결도 mermaid: `Vishamos · 10 / 11` → `Vishamos · 11`, `Body · 30` → `Body · 31`
- `[vs-Client-Ping]` "Pong 수신 시간(응답 유효 시간)" 아래 "응답 유효 시간." 줄 삭제(이제 ping 간격으로 판정), 클라이언트 다이어그램 `alt` 문구 "pong이 응답 유효 시간을 넘김" → "다음 ping까지 pong 없음", "재전송 횟수 만큼" → "미응답 허용 횟수만큼"

### `[vs-Client-CommonConnect]` (클라이언트 규칙, 서버 동작과 충돌 없음)
- "연결실패 → 재접속"에 설정 오류(주소 형식, 서버의 404 등록 거부)도 들어가 무한 재시도된다. 재시도할 실패(응답 없음·끊김)와 멈출 실패를 나누기

### DB
- `[vs-DB-Status]` "연결 지연율" 아래 "Synapse-DB-Ping을 통해" → `[vs-DB-Ping]`
- `[vs-DB-Ping]`의 `//` 질문 지우기 (답은 명세 02 §7.2.9b: MariaDB 프로토콜 ping, mysql2 `connection.ping()`)

### 사용자 답변 옮기기
명세 02에 "사용자 답변"으로 남은 결정. 옮겨지면 명세 근거를 노션 위치로 바꾼다.
- 인터넷 접속 없음(§3.1), 같은 시그니처 여러 개 접속(§5.1), 등록 인증 없음·집 기기만(§5.5d), 채팅 송신 제외(§7.1.4), 치지직 방송 관리는 나중(§7.1.5, 옛 번호 31이므로 "치지직 방송 관리"로 적기)

#### Q19. 컨트롤러(41)로 전달할 것 (노션 `VishasController`)
- 컨트롤러 자체(기술·구조·화면)는 컨트롤러 프로젝트에서 다룬다(2026-11-25 이관). 여기서는 서버가 컨트롤러에 **전달할 것**만 정한다. 1단계(`chzzk.chat`·`chzzk.status`)는 결정됨.
- 나중 후보
  1. 서버 에러 (노션 "추후 컨트롤러에 에러메세지 전송"). 정할 것: 붙일 정보(시그니처·연결 번호, 시각), 반복 에러 묶기(명세 02 §6.12b)
  2. 클라이언트 연결 상태(접속·끊김·지연, 명세 02 §5.7). 정할 것: 바뀔 때마다 알림 / 컨트롤러 요청 시 응답
- 컨트롤러가 서버로 관리 명령을 보내게 되면 권한(등록 인증 없음, 명세 02 §5.5d)을 먼저 정한다.
- 2026-11-27: 컨트롤러 간단 구현 완료, 로그·설정값을 Synapse로 통과시키려 함(노션 `VishasController` 로그 탭: "시냅스에서 보낸 시스템 로그만, 에러·경고·알림", 받은 쪽에서 민감 내용 가림). 정할 것
  1. (결정됨 2026-11-27, protocol README §5b)
  2. 서버 → 41 시스템 로그: 전부 보내기로 결정. 남은 것: `type`, 등급 분류, 41 등록 전 로그를 쌓아 둘지, 반복 묶기. 비밀 값은 **서버에서** 빼고 보낸다(받는 쪽 가림은 보조)
  3. 41 → 서버 설정 변경: 등록 인증이 없어 LAN의 누구나 41로 등록할 수 있다. 읽기만 / 안전한 항목만 변경 / 인증 먼저 중 선택. `.env`·DB·치지직 값은 변경 대상에서 뺀다

#### Q14. DB 작업 프로토콜의 요청 형식 (`[vs-DB-Protocol]`)
- **요약: 노션 요청 요소(Database·Table·ID)를 프로그램이 정하면 보안 위험. 사용자 인지함 — Synapse를 체계적으로 정리할 때 다룬다.**
- 해소된 부분 (명세 02 §7.2.11): 프로그램이 Synapse를 통해 DB 작업을 JSON으로 요청하고, 결과(0 성공 / 1 이상 실패, 실패 사유)를 "보내야 할 곳"으로 받는다.
- 추천(그때 참고): 미리 정한 작업 이름만 받는다. 예: `{"to": 0, "type": "db.viewer.get", "data": {"uid": "...", "replyTo": 10}}`. DB·테이블은 서버가 정하고, `secret_store`는 이 프로토콜로 접근할 수 없게 한다. `[vs-DB]` 페이지에 "메시지 처리" 절로 둔다(명세 §6.9).
- 정하려면: 작업 목록, 요청할 수 있는 프로그램과 쓰기 허용 범위, 실패 코드를 Q6과 합칠지.

#### Q11. 시청자 데이터의 필드와 보관
- 해소된 부분: 시청자 데이터를 저장한다 — 치지직 계정 UID와 UID별 일부 데이터, 개인정보 제외 (명세 02 §7.2.2). 추가·제거·수정을 한다 (`[vs-DB]` 핵심 루프).
- 정하려면
  1. "일부 데이터"는 무엇인가? (예: 첫 채팅 시각, 누적 채팅 수, soft currency 잔액)
  2. 언제 추가·수정·제거하는가? (예: 첫 채팅 시 추가, 채팅마다 수정, 시청자 요청 시 제거)
  3. 보관 기간
- 위험 (확인 필요, 추측 아님)
  - **UID가 개인정보가 아닌지는 단정할 수 없다.** 닉네임이나 채널 정보와 결합하면 특정 개인을 알아볼 수 있다. 저장 전에 치지직 Open API 이용 약관의 데이터 보관 조건을 확인한다(구현 전 Claude가 문서로 확인해 보고).
  - 닉네임을 함께 저장하면 개인정보 쪽으로 더 가까워진다. 꼭 필요한 필드만 둘 것.
- 태그 제안: `[vs-DB-Viewer]`

#### Q13. 배포·상주 방식
- 근거: 노션에 없음. 핵심 루프 "종료 호출 시 종료"
- 사용자 자문 (2026-11-17, 노션 반영 전): PC를 켜면 자동 시작, PC를 끄면 종료, 그 외에는 항상 켜 둠.
- 정하려면: (1) Node로 직접 실행 / 단일 실행 파일, (2) 아래 고려 사항 중 무엇을 할지
- 고려 사항
  - **종료 시 토큰 저장 대기:** 치지직 Refresh Token은 1회용. 종료 신호(Ctrl+C, 콘솔 닫힘, OS 종료)를 받으면 진행 중인 저장만 짧게 기다린다. 접속한 프로그램 알림은 불필요(자동 재접속).
  - **비정상 종료 시 자동 재시작**, **이중 실행 방지**(포트 충돌), **로그 파일**(나중에 VishasController), **수동 재시작 방법**
  - 부팅 직후 DB 미준비는 DB 무한 재시도로 해결됨.
- 추천: Node 직접 실행 + Windows 작업 스케줄러(로그온 시 시작, 실패 시 재시작). 위 고려 사항 모두 포함.
- 태그 제안: `[vs-Deploy]`

## 태그 목록 (확정 2026-11-18, 접두어 변경 2026-11-27)

- 2026-11-27 사용자가 노션에서 접두어를 `Synapse-` → `vs-`로 바꿨다(VishaSynapse의 "내부 태그 축약"). 뒷부분 이름은 그대로라 `[Synapse-X]` = `[vs-X]`. 커밋 메시지에 남은 옛 접두어는 그대로 둔다.
- 다른 프로젝트 태그(`[vc-…]` 컨트롤러 등)는 이 표에 넣지 않는다.

태그는 기획 항목에 붙이는 이름이며 작업 단위가 아니다. 새 내용을 노션에 쓸 때 아래 영역 안에서 이름을 지어 붙이고 이 표에 추가한다. 형식은 `[vs-DB-Connect]`처럼 이름형이며, 같은 이름을 두 번 쓰지 않고, 한 번 붙인 이름은 바꾸지 않고, 폐기한 이름은 다시 쓰지 않는다.

| 영역 (작업 번호 접두어) | 사용 중 | 내용이 생기면 붙일 예정 |
|---|---|---|
| 중계 서버 (`Relay`) | `[vs-Loop]`, `[vs-Message]`, `-Message-Signature`, `-Message-Type`, `-Message-Error`, `-Message-Command`, `-Message-Relay`, `[vs-Client]`, `-Client-Status`, `-Client-Ping` | |
| DB (`DB`) | `[vs-DB]`, `-DB-Connect`, `-DB-Protocol`, `-DB-Ping`, `-DB-Status` | `-DB-Viewer` (Q11) |
| 치지직 (`Chzzk`) | `[vs-Chzzk]` | |
| OBS (`OBS`) | `[vs-OBS]` (보류) | |
| Discord (`Discord`) | `[vs-Discord]` (보류) | |
| 입력 (`Input`) | | `[vs-Input]` (#4) |
| 배포·상주 (`Deploy`) | | `[vs-Deploy]` (Q13, 종료 포함) |
