### Message와 Relay 나누기 (사용자 요청 2026-11-17)
- **Message = 메시지 모양** (보내는 쪽·받는 쪽이 지킬 형식). **Relay = 서버가 받은 뒤 하는 일** (누구에게, 어떤 조건으로 전달하는가).
- 지금 노션은 전달 규칙이 세 곳에 흩어져 있다: `[Synapse-Message]` "서버는 서버가 읽을것만 체크하고 전달", 시그니처 표 비고(10 → 10+11, 20 → 21+22), `[Synapse-Client]` "해당하는 배열에 모두 전송".
- 제안: 노션 섹션을 넷으로 나누고, 세부 태그는 줄인다 (메시지 헤더가 단순해져 `-Binary`·`-Text`·`-Sender`는 규격 표 한 장으로 충분).

## A. 명세 02 승인 전에 필요

### 메시지·전달

#### Q3. 메시지 형식: 서버에 필요한 것만
- **요약: 헤더 규격(바이너리 `[To, From] + 데이터`, JSON `To·From·Type·data`)은 확정(명세 02 §6). 메시지 내용(앱끼리 주고받는 명령, 바이너리 종류·배치)은 다른 프로그램을 만들면서 정한다(사용자 2026-11-17). 서버는 헤더만 읽으므로 그것 없이도 구현할 수 있다. 지금 정할 것은 서버가 직접 주고받는 메시지 4가지.**
- 질문
  1. **등록 메시지:** 등록·등록 완료를 JSON으로 하는가? 서버가 먼저 보내던 `[0, 0]`은 없애는가? (명세 02 §5.5 해석)
  2. **서버가 보내는 메시지의 `Type`:** 등록 완료, 에러(Q6), DB 결과도 받는 쪽이 구분하려면 `Type`이 필요하다. "Type(도착지가 서버면)"을 "Type(서버가 보내거나 받을 때)"로 넓히는가?
  3. **서버가 처리하는 목적지:** 치지직(31)·OBS(51)로 가는 JSON도 서버가 처리하므로 `Type`이 필요하다. "서버가 처리하는 목적지 = 00·31·51"로 묶는가?
  4. **표기:** JSON 키 대소문자(`To`/`to`), 바이너리 숫자 바이트 순서(리틀 엔디언).
- 추천: 1 JSON으로, `[0, 0]` 없앰. 2 넓힘. 3 묶음. 4 소문자 `to·from·type·data`, 리틀 엔디언.
- 옛 "처리 받을 메세지 타입" 목록(`00`·`01`·`21`)은 새 규격과 맞지 않는다(바이너리에 타입 없음). 위 1·2가 정해지면 서버 명령(등록 등)만 남기고, `21 Face Data`는 Face·Vishamos를 만들 때 Vishamos 페이지로 옮긴다.
- 프로그램을 만들 때 참고 (자문 기록): JSON은 명령, 바이너리는 ① 초당 10회 이상 연속 ② 큰 숫자 배열 ③ 지연 민감일 때. 바이너리 종류 번호와 데이터 배치는 받는 쪽 페이지 표에 한 줄씩(기기 시그니처와 별개). Face 송신은 `[0a, 15, …]` → `[0a, 출처, 15, …]`로 바뀌어 Vishamos·VishaFace 수정 필요.
- 취약한 부분(명세 02 §8.1) 중 이번 범위: 서버에서 막을 수 있는 1·2·3·4·7 (`제안`). 5는 받는 쪽 표로, 6은 위 4번으로, 8은 Q6.
- 태그 제안: `[Synapse-Message-Type]` (서버 명령 목록. 앱 명령은 프로그램을 만들며 늘어남)
- 완료 기준: 노션에 1~4 답.

#### Q16. 전달 규칙과 묶음 시그니처
- **요약: 시그니처 표에 묶음 값이 생겼다(10 = 본방 + 테스트, 20 = Galaxy + Iphone). 서버가 목적지를 어떻게 펼칠지 규칙이 필요하다.** 근거: `[Synapse-Message]` 시그니처 표 비고, `[Synapse-Client]` "해당하는 배열에 모두 전송"
- 질문
  1. **일반 규칙인가, 개별 지정인가?** "끝자리 0 = 같은 십의 자리 전체"(10 → 1x, 20 → 2x)로 일반화하는가, 표에 적힌 것만인가? 일반화하면 30·50 등도 자동으로 묶음이 된다. (00은 서버라 예외)
  2. **등록할 수 있는 값:** 10은 묶음이면서 본방 Vishamos의 등록 값이기도 하다. 20은 등록하지 않는 목적지 전용 값으로 보면 되는가?
  3. **전달 규칙 정리 위치:** 위 "Message와 Relay 나누기"처럼 `[Synapse-Relay]` 섹션을 두는가?
- 추천: 1 표에 적힌 것만(묶음 열을 추가해 `10 → 10, 11`, `20 → 21, 22`처럼 명시). 일반 규칙은 나중에 값이 늘 때. 2 그렇게 봄. 3 둠.
- 태그 제안: `[Synapse-Relay]`, `[Synapse-Signature]`
- 완료 기준: 노션 시그니처 표에 묶음 대상 명시, 등록 가능 여부, 전달 규칙 섹션.

#### Q7. 메시지 크기·빈도 한도
- 해소: 본방/개발 동시 사용은 시그니처(10·11)로 나눈다(명세 02 §5.3). Galaxy·Iphone 동시 송신은 `From`으로 구분된다.
- 질문: Face 메시지 하나의 최대 크기와 초당 횟수는? (현재 87바이트, 초당 10회)
- 추천: 서버 한도를 넉넉히(예: 64KB) 잡고 실측 후 조정(`제안`). 넘으면 버리고 에러(Q6).
- 태그 제안: `[Synapse-Relay]` 안에 적음
- 완료 기준: 노션에 한도 또는 "기본값 사용".

### 클라이언트

#### Q2. 프로그램 연결 체크
- 노션 원문은 그림으로 바뀌며 "주기적으로 연결 체크"와 `//` 자문이 빠졌다. 그림은 꾸미기라 근거로 보지 않으므로, 서버 ping 방식은 명세 02 §5.6에 해석으로 둔다.
- 남은 질문: 서버가 ping하는 방식이 맞는지, ping 간격, 끊는 조건(시간·횟수), 등록 제한 시간(접속 후 N초 안에 등록 안 하면 끊음), 왕복 지연(ms) 표시 여부.
- 추천 (`제안`, 조정 가능한 기본값): 간격 10초(DB는 30초지만 클라이언트는 실시간 데이터라 끊김을 빨리 아는 편이 낫다), 다음 ping까지 pong이 없으면 끊음, 등록 제한 30초(현재 코드 값), 왕복 지연은 DB처럼 ms로 표시.
- 참고: Unity `ClientWebSocket`은 ping에 자동으로 pong을 돌려주므로 클라이언트 앱 수정은 필요 없다.
- 태그 제안: `[Synapse-Client-Ping]`
- 완료 기준: 노션 `[Synapse-Client]`에 간격·끊는 조건·등록 제한 시간 (기본값으로 둔다면 "기본값 사용"만 적어도 됨).

#### Q5. LAN 기기의 등록 인증
- 근거: 송출컴의 서버에 휴대폰·게임컴이 같은 공유기 안에서 접속한다 (명세 02 §3.2). 지금은 LAN 안의 아무 기기나 등록할 수 있다.
- 질문: 등록할 때 공유 키를 확인하는가?
- 추천: 공유 키 확인. 값은 `.env`의 `ENV_RELAY_KEY`(가칭)에 둔다.
- 태그 제안: `[Synapse-Client-Auth]`
- 완료 기준: 노션 `[Synapse-Client]`에 인증 여부.

#### Q6. 에러 메시지

#### Q10. OBS 연결 세부 (`[Synapse-OBS]`)
- 해소: 서버가 obs-websocket으로 OBS를 직접 관리한다. 목표는 연결, 소스·장면 목록, 장면 전환 (명세 02 §7.3). 노션 "server to server 일거같다" → OBS가 WebSocket 서버, Synapse가 클라이언트로 접속하는 구조.
- 남은 질문
  1. 연결 실패·끊김 처리: DB와 같은 틀인가?
  2. obs-websocket 비밀번호: OBS에서 인증을 켜면 비밀번호가 필요하다. 비밀 값이므로 `secret_store`(치지직과 같은 곳) 또는 `.env`(`ENV_OBS_PASSWORD`, 가칭)에 둔다.
  3. 장면 전환은 누가 요청하는가? (예: Vishamos가 JSON `to: 51, type: "obs.scene"`) → Q3-4
  4. input-overlay(Q15)와 같은 OBS지만 별개 연결이다. 시그니처 51을 둘 다에 쓰는가?
- 추천: 1 DB와 같은 틀. 2 `secret_store`. 3 JSON 명령 목록에 OBS 명령 추가. 4 Q15 추천대로 입력용 값 분리.
- 완료 기준: `[Synapse-OBS]`에 1~3.

#### Q15. 게임컴 입력 (input-overlay 경유)
- **요약: 흐름 `게임컴 → io_client → OBS input-overlay → Synapse → Vishamos`가 노션 연결도에 반영됐다(17:20). Synapse가 input-overlay에 클라이언트로 접속하는 새 연결이 생긴다. 남은 것은 아래 1~4.**
- 질문
  1. 직접 관리 요소에 input-overlay 연결을 추가하는가? (`[Synapse-OBS]`에 같이 둘지, 따로 둘지)
  2. 연결 실패·끊김 시 동작 (DB와 같은 틀?)
  3. 시그니처: `51 : OBS`를 같이 쓰는가, 입력용 값을 새로 두는가?
  4. Vishamos에 넘길 입력: 키 누름/뗌만? 마우스·게임패드도? (input-overlay는 마우스 이동까지 전부 보냄 → Synapse가 걸러서 우리 형식으로 변환)
- 추천: 1 `[Synapse-Input]`으로 따로. 2 DB와 같은 틀. 3 입력용 새 값. 4 키 누름/뗌만 JSON으로 시작(`제안`). 키 입력 내용은 로그 금지.
- 조사 기록 (2026-11-17, input-overlay 저장소·위키): `io_client`는 바이너리(라이브러리 구조체를 그대로 복사, 문서화된 규격 아님), 마우스 이동 무필터, 암호화·인증·재접속 없음. 플러그인은 받은 입력을 JSON WebSocket으로 다시 내보낸다(필드·포트는 구현 전 Claude가 `data/example.html`로 확인). io_client를 Synapse에 직접 붙이는 것은 비추천.
- 보안 프로그램 탐지 (자문 기록): 공식 허용 목록 없음. 위험한 것은 게임 프로세스 주입·메모리 읽기·입력 생성·주입형 훅. io_client는 저수준 훅으로 읽기만 하며, 사용 이력(FPS 스트리머)이 직접 제작보다 나은 점. 수칙: 입력 생성 기능 없음, 관리자 권한 실행 안 함, Vanguard 계열 게임은 공식 안내 확인. 문제가 생기면 Raw Input 방식으로 직접 제작.
- 태그 제안: `[Synapse-Input]`
- 완료 기준: 노션 직접 관리 요소 갱신, 1~4 답.

#### Q14. DB 작업 프로토콜의 요청 형식 (`[Synapse-DB-Protocol]`)
- **요약: 노션 요청 요소(Database·Table·ID)를 프로그램이 정하면 보안 위험. 사용자 인지함 — Synapse를 체계적으로 정리할 때 다룬다.**
- 해소 (명세 02 §7.2.11): 프로그램이 Synapse를 통해 DB 작업을 JSON으로 요청하고, 결과(0 성공 / 1 이상 실패, 실패 사유)를 "보내야 할 곳"으로 받는다.
- 추천(그때 참고): 미리 정한 작업 이름만 받는다. 예: `{"to": 0, "type": "db.viewer.get", "data": {"uid": "...", "replyTo": 10}}`. DB·테이블은 서버가 정하고, `secret_store`는 이 프로토콜로 접근할 수 없게 한다.
- 남은 질문: 작업 목록, 요청할 수 있는 프로그램과 쓰기 허용 범위, 실패 코드를 Q6과 합칠지.

#### Q11. 시청자 데이터의 필드와 보관
- 해소: 시청자 데이터를 저장한다 — 치지직 계정 UID와 UID별 일부 데이터, 개인정보 제외 (명세 02 §7.2.2). 추가·제거·수정을 한다 (`[Synapse-DB]` 핵심 루프).
- 남은 질문
  1. "일부 데이터"는 무엇인가? (예: 첫 채팅 시각, 누적 채팅 수, soft currency 잔액)
  2. 언제 추가·수정·제거하는가? (예: 첫 채팅 시 추가, 채팅마다 수정, 시청자 요청 시 제거)
- 위험 (확인 필요, 추측 아님)
  - **UID가 개인정보가 아닌지는 단정할 수 없다.** 닉네임이나 채널 정보와 결합하면 특정 개인을 알아볼 수 있어 개인정보로 볼 여지가 있다. 저장 전에 치지직 Open API 이용 약관의 데이터 보관 조건을 확인해야 한다.
  - 닉네임을 함께 저장하면 개인정보 쪽으로 더 가까워진다. 꼭 필요한 필드만 둘 것.
- 태그 제안: `[Synapse-DB-Viewer]`
- 완료 기준: `[Synapse-DB]`에 필드 목록과 추가·수정·제거 시점, 보관 기간. (약관 확인은 구현 전 Claude가 문서로 확인해 보고)
