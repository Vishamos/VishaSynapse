## 5. 다중 접속 (`[Synapse-Client]`)

| # | 내용 | 구분 | 근거 |
|---|---|---|---|
| 5.1 | 같은 식별값의 클라이언트가 여러 개 접속할 수 있다. (본방용은 계속 켜 두고, 개발 중인 것을 함께 붙여 확인) | 확정 | 사용자 답변 |
| 5.2 | 클라이언트는 시그니처별 배열로 등록해 두고, 메시지의 목적지에 해당하는 배열에 **모두** 전송한다. | 확정 | `[Synapse-Client]`, `[Synapse-Message-Relay]` |
| 5.3 | 본방·테스트를 구분하는 시그니처는 없다. 테스트 클라이언트도 같은 시그니처로 등록해 함께 받는다. | 확정 | `[Synapse-Message-Signature]`, 사용자 답변 |
| 5.4 | 등록 절차: 클라이언트가 등록 전송 → 서버가 등록 후 완료 전송 → 연결 확인. 이후 JSON/Binary 송수신, 앱 종료 또는 서버 종료로 연결 종료. | 확정 | `[Synapse-Client]` |
| 5.5 | 접속 후 클라이언트가 먼저 등록을 보낸다. 서버가 먼저 보내는 메시지(옛 코드의 `[0, 0]`)는 없앤다. | 확정(승인) | `[Synapse-Client]`. 등록 절차가 클라이언트 전송으로 시작하므로 |
| 5.5a | 등록: 클라이언트 → 0, JSON `type: client.register`. 등록 완료: 0 → 클라이언트, `type: client.registered`. | 확정 | `[Synapse-Message-Type]` |
| 5.5b | 등록할 시그니처는 `client.register`의 `from` 값이다. 서버는 그 값의 배열에 클라이언트를 등록한다. | 확정 | `[Synapse-Client]` |
| 5.5c | 등록에 성공하면 배열에 추가하고, 연결 번호를 1 늘려 그 값을 `client.registered`의 `data.index`로 보낸다. 연결이 끊기면 배열에서 빼지만 번호는 줄이지 않는다(재사용 안 함). | 확정 | `[Synapse-Client]`, `[Synapse-Message-Type]` |
| 5.5c-1 | 연결 번호는 시그니처와 관계없이 서버 전체에서 하나로 센다. 서버를 다시 시작하면 처음부터 센다. | 확정(승인) | `[Synapse-Client]`. 번호의 범위가 정해져 있지 않아 가장 단순한 쪽으로 |
| 5.5d | 등록 인증은 하지 않는다. 등록 메시지는 `from`(시그니처)만 담고 `data`는 비어 있다. | 확정 | `[Synapse-Message-Type]`, 사용자 답변(집 기기만 씀) |
| 5.5e | 등록하지 않은 클라이언트가 보낸 메시지는 전달하지 않고 에러(401)를 돌려준다. | 확정 | `[Synapse-Message-Signature]`, `[Synapse-Message-Relay]` |
| 5.5f | 표에 없는 시그니처로 등록하면 거부하고 에러(404)를 돌려준다. | 확정 | `[Synapse-Message-Error]` |
| 5.6 | 연결 체크는 WebSocket ping/pong으로 한다. 서버가 ping을 보내고 클라이언트 라이브러리가 자동으로 pong을 돌려준다. 클라이언트가 따로 ping을 보낼지는 각 클라이언트가 정한다. | 확정 | `[Synapse-Client-Ping]` |
| 5.6a | ping 간격: 기본 30초 | 확정 | `[Synapse-Client-Ping]` |
| 5.6b | pong 응답 유효 시간을 넘기면 상태를 "연결 지연"으로 바꾼다. pong을 받은 시각을 기록한다(나중에 표시). | 확정 | `[Synapse-Client-Ping]` |
| 5.6c | ping은 응답과 관계없이 간격마다 항상 보낸다. pong 없이 지나간 ping이 미응답 허용 횟수(기본 5회, 마지막 pong 이후 약 2분 30초∼3분)에 이르면 연결을 끊는다(배열에서 제거). 구현은 마지막 pong 시각만 기록하고 간격마다 경과 시간을 비교하면 된다. | 확정 | `[Synapse-Client-Ping]` |
| 5.6d | `Delay` 판정은 별도 시간 없이 ping 간격을 쓴다: 다음 ping을 보낼 때까지 pong이 없으면 `Delay`, 미응답 허용 횟수(5회)에 이르면 해제. pong 수신 시각을 기록해 왕복 시간(ms)을 지연 표시에 쓴다. | 확정 | `[Synapse-Client-Ping]` |
| 5.7 | 클라이언트 연결 상태: `Connecting`(연결 시도 중) / `Connected`(연결됨) / `Delay`(지연됨) / `Disconnect`(연결 해제) | 확정 | `[Synapse-Client-Status]` |
| 5.7a | 서버 쪽에서 `Connecting`은 접속 후 등록 전, `Connected`는 등록 완료 후, `Delay`는 다음 ping까지 pong이 없음(§5.6d), `Disconnect`는 해제 처리 중(배열에서 빠지기 직전)으로 본다. pong이 다시 제때 오면 `Delay` → `Connected`. | 확정(승인) | `[Synapse-Client-Status]`. 상태 이름만 있고 전이가 없어 §5.6b·5.6c와 맞춤 |
| 5.8 | 접속 후 30초 안에 등록 메시지를 받지 못하면 연결을 끊는다(종료 코드 1008). | 확정 | `[Synapse-Client]`, `[Synapse-Message-Error]` |

| 6.1 | 간단한 명령은 JSON 메시지, 실시간 갱신 데이터는 바이너리로 보낸다. | 확정 | `[Synapse-Message]` |
| 6.2 | JSON: 서버가 읽는 것은 `to`, `from`, `type`(도착지가 서버일 때), 나머지는 `data` | 확정 | `[Synapse-Message]` |
| 6.2a | JSON 키 이름은 소문자 `to`·`from`·`type`·`data`. | 확정(승인) | `[Synapse-Message-Type]`. 규격 표의 대문자 표기와 다르므로 Type 표를 따름 |

**앱 메시지를 만들 때 참고 (자문 기록 2026-11-17, 서버 범위 밖)**
- JSON은 명령, 바이너리는 ① 초당 10회 이상 연속 ② 큰 숫자 배열 ③ 지연에 민감할 때.
- 바이너리 종류 번호와 데이터 배치는 받는 쪽 페이지 표에 한 줄씩 적는다(기기 시그니처와 별개).
- Face 송신은 `[0a, 15, …]` → `[to, from, 15, …]`로 바뀌므로 Vishamos·VishaFace 수정 필요. 등록도 JSON으로 바뀌므로 두 앱의 등록 코드를 고치고, `[0, 0]`을 기다린 뒤 등록하는지 구현 때 확인한다(§5.5). 시그니처 값도 바뀌었다(Vishamos 11, Body 31).
- Body(31): 별도 저장소 Vishas_Capture. 프레임당 바이너리 약 1,076바이트 + 헤더 2 = 1,078바이트, 초당 30회(그쪽 설계 메모). Synapse에는 WebSocket으로 접속하고, 끊김이 실제로 보이면 서버 쪽 UDP 수신을 검토한다(Unity 직접 UDP는 본방·테스트 동시 수신이 안 돼 비추천). Vishamos 수신 버퍼(1KB, §8.1-4)를 넘으므로 Vishamos 수정 필요.
- 클라이언트용 프로토콜 문서: 통신 규칙의 기준은 이 저장소다. 명세 승인 후 클라이언트가 지킬 부분만 `docs/protocol/`에 따로 둔다(Vishas_Capture 등 클라이언트 프로젝트가 읽음). 공개 저장소이므로 내부 주소·경로는 넣지 않는다.
- 직접 관리 요소별 Type(예: `db.viewer.get` → `db.viewer.get.result`, `obs.scene.set`, `chzzk.chat`)은 각 페이지의 "메시지 처리"에 둔다(§6.9). ping은 WebSocket 자체 ping/pong이라 Type 없음.

## 8. 옛 코드 동작 (참고, 기획 아님)

C6∼C11 재작성 전 코드의 동작이다. 클라이언트 앱을 고칠 때 참고한다.

- 연결 직후 서버 → 클라이언트 `[0, 0]`, 클라이언트는 30초 안에 `[0, 1, 식별값]`으로 등록, 서버 응답 `[0, 1]`. 미등록 시 연결 종료.
- 첫 바이트가 목적지. 0이 아니면 같은 식별값 클라이언트에게 그대로 전달.
- 텍스트 메시지는 처리 경로가 동작하지 않음.
- 기존 클라이언트(2026-11-17 확인, `Vishamos/Vishamos`·`Vishamos/VishaFace`): 얼굴 데이터 `[0a, 15, 감지 0/1, float32 x·y·z × 7점]` 87바이트를 0.1초마다 Face → Vishamos. 클라이언트는 10초마다 자동 재접속. 새 규격(§6.4)으로 바꾸려면 두 앱 모두 수정 필요.

### 8.1 옛 코드의 취약한 부분 (2026-11-17 확인)
LAN 전용 서버라 상세를 적는다 (§3.1). 서버 쪽은 C6∼C11에서 고쳤고, 클라이언트 쪽 항목은 앱 수정 때 참고한다.
1. 등록 전에도 전달된다. → §5.5e
2. 식별값은 자기 신고, 재등록으로 변경 가능, 표에 없는 값도 받음. → §5.5f
3. 길이 검사 없음. 1바이트 메시지가 그대로 전달되어 받는 쪽(Vishamos 수신부는 길이 확인 없이 `[1]` 읽음)에서 예외.
4. 크기 상한 없음(ws 기본 100MiB). 받는 쪽은 1024바이트 버퍼에 한 번만 읽고 `EndOfMessage`를 확인하지 않아 1KB 초과 메시지가 깨진다. → §6.5
5. 페이로드 규격이 한곳에 없음. Vishamos의 얼굴 데이터 해석 함수가 Face 송신 형식과 1바이트 어긋나 있다(시작 위치 4 vs 3, 호출하는 곳은 없음).
6. 바이트 순서 미명시(`BitConverter`는 기기 기본 순서, 현재 기기는 모두 리틀 엔디언). → §6.4b
7. 텍스트도 Buffer로 들어와 바이너리 처리로 넘어간다(ws 8). JSON `{`(123)가 목적지로 읽힐 수 있다. → §6.1
8. 실패 알림 형식이 섞여 있다(성공은 바이너리 `[00, 01]`, 시간 초과는 텍스트 `'Fail to Initialize.'`). → §6.12
