## 8. 현재 코드 동작 (참고, 기획 아님)

명세가 확정되면 아래는 바뀔 수 있다. 정리 작업은 worklist C 그룹.

- 연결 직후 서버 → 클라이언트 `[0, 0]`(= 노션 `00 Send Handshake`로 보임), 클라이언트는 30초 안에 `[0, 1, 식별값]`(= `01 Socket Client Init.`)으로 등록, 서버 응답 `[0, 1]`. 미등록 시 연결 종료.
- 첫 바이트가 목적지. 0이 아니면 같은 식별값 클라이언트에게 그대로 전달.
- 텍스트 메시지는 처리 경로가 동작하지 않음 (worklist C1).
- 기존 클라이언트(2026-11-17 확인, `Vishamos/Vishamos`·`Vishamos/VishaFace`): 얼굴 데이터 `[0a, 15, 감지 0/1, float32 x·y·z × 7점]` 87바이트를 0.1초마다 Face → Vishamos. 클라이언트는 10초마다 자동 재접속. 새 규격(§6.4)으로 바꾸려면 두 앱 모두 수정 필요.

### 8.1 현재 코드의 취약한 부분 (2026-11-17 확인, 구현 때 참고)
LAN 전용 서버라 상세를 적는다 (명세 02 §3.1).
1. 등록 전에도 전달된다 (`VSHandler.js:71-79`). → C4, plan_review Q5
2. 식별값은 자기 신고, 재등록으로 변경 가능, 표에 없는 값도 받음.
3. 길이 검사 없음. 1바이트 메시지가 그대로 전달되어 받는 쪽(Vishamos 수신부는 길이 확인 없이 `[1]` 읽음)에서 예외. → C3
4. 크기 상한 없음(ws 기본 100MiB). 받는 쪽은 1024바이트 버퍼에 한 번만 읽고 `EndOfMessage`를 확인하지 않아 1KB 초과 메시지가 깨진다. → plan_review Q7
5. 페이로드 규격이 한곳에 없음. Vishamos의 얼굴 데이터 해석 함수가 Face 송신 형식과 1바이트 어긋나 있다(시작 위치 4 vs 3, 호출하는 곳은 없음).
6. 바이트 순서 미명시(`BitConverter`는 기기 기본 순서, 현재 기기는 모두 리틀 엔디언).
7. 텍스트도 Buffer로 들어와 바이너리 처리로 넘어간다(ws 8). JSON `{`(123)가 목적지로 읽힐 수 있다. → C1
8. 실패 알림 형식이 섞여 있다(성공은 바이너리 `[00, 01]`, 시간 초과는 텍스트 `'Fail to Initialize.'`). → plan_review Q6
